# Sealed Lists — Agent Guide

Read [README.md](README.md) first for what the product does and its trust model. This file covers what is easy to break.

## Product boundary

Sealed army list submission for Warhammer 40,000, and nothing else. Lists are opaque text: no parsing, no validation, no points totals, no faction or detachment awareness, no list building. Anything that needs to understand the contents of a list belongs in a different tool.

## Commands

- `pnpm check` — the full gate (format, lint, `db:check`, build, typecheck, tests). Build runs before typecheck because it generates `src/routeTree.gen.ts`; on a fresh clone typecheck fails until you build.
- Dev server: `DATA_DIR=./data-dev pnpm dev` (create the directory first).
- Lint and format are oxlint + oxfmt, not ESLint/Prettier. Warnings are denied.

## Load-bearing rules

- **`src/core/game.ts` is the whole domain** — limits, retention, list normalization, types, and `gameView`. It stays free of IO and framework imports.
- **`gameView` is the only place visibility is decided.** A list reaches exactly two audiences: its owner, and everyone once the game reveals. Route components and server functions must not reassemble a view by hand.
- **An entry holds a `list` or a `draft`, never both.** Sealing moves the text into `list` and clears `draft`; unsealing moves it back. A draft is work in progress and reaches exactly one person, so it is carried as `GameView.viewerDraft` and deliberately kept out of `entries` — there is no state, revealed included, in which anyone else may see one, and keeping it off the per-player shape means a future field cannot leak it by accident.
- **Unsealing is what makes editing safe.** `Service.unsealList` takes the entry out of the sealed count, so a game cannot complete while its author is part way through changing their mind. Anything that lets someone edit a sealed list must unseal first, or it reintroduces the race where the last player seals and reveals a list its owner had already moved on from.
- **Presence lives in memory, never in SQLite.** `src/server/presence.ts` is the live state of the open event streams: arriving and leaving _is_ a stream opening and closing, which is why there are no heartbeats and nothing to expire except the typing flag. A row in the database would outlive the tab it describes. Presence carries names and a typing flag and nothing else — never a word of anyone's list.
- **Identity is the session, membership is the authorization.** better-auth (`src/server/auth.ts`) owns accounts; `requireUser()` in `src/server/session.ts` gets the signed-in user, and `Service.requireMembership` decides what they may touch. The group link is an invitation: it grants seeing the group's name, its members, and the right to join — nothing more. `groupView` deliberately returns `currentGame: null` and empty `pastGames` to a link holder who has not joined, so a leaked link never exposes a list. A signed-out visitor gets the sign-in prompt only when the link leads somewhere: `fns.group` checks `hasGroup` first, because otherwise a mistyped link invites someone to a group that does not exist. That check tells an anonymous visitor nothing they did not already have — the token is unguessable, so holding it is the only way to ask.
- **better-auth owns its five tables** (`user`, `session`, `account`, `verification`, `rateLimit`). Their shapes come from better-auth, so never add product columns to them; hang product tables off `user.id` instead.
- **The reveal happens inside the repository transaction** (`Repository.sealList`, `Repository.dropEntry`). Deciding "was that the last list?" outside the transaction races two simultaneous submissions.
- **A group runs one game at a time**, enforced in `Repository.createGame`'s transaction. `groupView` then shows the collecting game, or the most recently revealed one, so a reveal lands on the page the group is already looking at instead of vanishing into history.
- **Revealed games are immutable**: sealing, joining and dropping all check `revealedAt` first. Every new mutation must too. Deleting is the exception and is deliberate — `Service.deleteGame` works at any stage, because a game nobody is going to finish would otherwise block the group forever (one game at a time), and history is the group's to clear. It takes the lists with it via the cascade, so the confirmation says so.
- **Game numbers describe what is there, not how many there have ever been.** `createGame` takes `max(number) + 1` over surviving games, so deleting the newest frees its number again and deleting a middle one leaves a gap. Both are honest; do not add a separate counter to make them contiguous.
- **A group keeps one member, not two.** `MEMBERS_MIN` is 1: requiring two would trap the pair in a two-player group, which is the most common size a group has. A _game_ still needs `PLAYERS_MIN` (2) — the two limits are different things and neither should be expressed with the other's constant. The last player cannot leave, so `Service.deleteGroup` is their way out; any member may call it, the same as removing someone or deleting a game, because this app has no roles.
- **`entries.user_id` points at the account, not at group membership.** That is what lets someone leave a group — a plain delete of their `group_members` row — without erasing their lists from games that already revealed. Never re-key entries to membership.
- **Nothing derived is stored.** A column that can be computed from the list text is a regression.
- **Reads answer `null`, mutations throw.** The view server functions wrap the service in `orNull` so a wrong or expired link becomes `null`, which the route turns into `notFound()` and a real 404. Throwing a `Response(404)` from a loader would surface as a 500 instead.
- **Making a game is "New game", and it lives in a dialog.** What it creates really is the next game, so it says so — but the app collects lists and never runs anything you play, which is what "Start a game" and "Start with 3" wrongly implied. The dialog carries that explanation, and the trigger only appears where there is no collecting game to confuse it with: in the empty state, or in the header once the last lot is open. Never as a card underneath a game, which is what made it read as an action on the game on screen.
- **Live updates are a nudge, never a payload.** `/api/events` sends `event: change` with a meaningless body; the page then refetches through `groupQuery` and `gameView` decides what it may see. Putting anything about a list into the stream would put a second visibility decision next to the only one. The one message that does carry data is `event: presence`, whose entire vocabulary is names and a typing flag. The stream is members-only, so a leaked link buys no stream, and `StreamLimiter` bounds how many any account may hold open. `groupQuery` therefore has no `refetchInterval` — do not add polling back.
- **Drafts save themselves, on a debounce, and flush on the way out.** `useDraft` waits for typing to settle rather than throttling through it, and flushes on hide and unmount so closing a tab cannot cost the last sentence. Saving a draft doubles as "stopped typing", which is why the typing ping only fires while typing continues. A failed save is swallowed: the text is still on screen and the next keystroke retries.
- **The UI explains nothing about its own mechanics.** No hashes, no jargon, no "how it works" — players get plain statements of what is true now ("Sealed", "Nobody can change a list now"). Technical detail belongs in this file and the README, whose readers are developers.
- **Nothing expires.** Lists are text and text is cheap, so there is no retention sweep and no scheduled deletion anywhere; games and groups stay until someone deletes them. Do not reintroduce a TTL without being asked. Cascades still matter: `entries` hangs off `games`, and `group_members` off `groups`, so removing a parent takes its children.
- **Server functions wrap handlers in `rpc()`** — a thrown `Response` otherwise reaches the client as a successful result — and every mutation calls `requireMutationOrigin()` first. CSRF protection is per-function, not middleware.
- **Never log a group token or a session cookie**, and never put either in an error message.
- **`src/styles.css` owns the bridge from the `:root` tokens to Tailwind's colour utilities** (`@theme inline { --color-primary: var(--primary) … }`). shadcn ships no `tailwind.css` to import: without that block every `bg-primary`, `bg-card` and `border-border` inside the components silently resolves to nothing, and the whole UI renders flat and colourless.
- **Themed primitives, not per-page classes.** Display type, uppercase tracking and thumb-sized controls live in `button.tsx`, `badge.tsx`, `label.tsx`, `input.tsx` and `textarea.tsx`, so pages stay plain. Anything rendering a person's name adds `normal-case` — never uppercase user-entered text.
- **UI is shadcn (Base UI) under `src/components/ui`.** Those files are generated by `pnpm exec shadcn add` and excluded from lint; four diverge on purpose and the reasons are commented in place: `sonner` is pinned to dark, both dialog backdrops are darkened because the generated 10% black does nothing over a near-black page, and `separator` is sized off its prop because the generated `data-horizontal:` variants match an attribute Base UI does not emit.
- **A Tailwind variant that names a data attribute is only real if the library writes it.** Base UI emits `data-orientation`, `data-open`/`data-closed`, `data-checked`/`data-unchecked`, `data-side`, `data-popup-open`; a class like `data-horizontal:h-px` silently compiles and silently does nothing, which looks like a design problem rather than a bug. When a generated component renders flat, measure the element in a browser before touching the CSS.
- **`/g/$token` is a page, not a layout.** It renders no `<Outlet />`, so any route file nested under it in the flat naming — `g.$token.something.tsx` — renders nowhere: the URL changes and the group page stays on screen, on a direct visit too. That is why the finished-game page is `g.$token_.game.$gameId.tsx`; the trailing underscore keeps the URL and lifts the route to the root. Nothing catches this — it builds, typechecks and lints clean — so a new page under `/g/$token/…` has to be clicked in a browser.
- **A link that navigates must be an anchor.** `<Button render={<Link/>}>` makes Base UI stamp `role="button"` on the anchor, which lies to screen readers. Style the `Link` with `buttonVariants()` instead.
- **Confirmations are `ConfirmButton`, never `window.confirm`.**
- **Every optional dependency degrades honestly, and silently.** No SMTP settings means no email, no password-reset link, and no email section on the account page at all — not a card explaining that the instance cannot send mail, which is the operator's business and not the player's. No provider credentials means no provider button. Read what is available through `signInOptions`, never assume it in the UI.
- **A page whose subject can be deleted leaves through `useGone`.** `notFound()` thrown from a render lands in the error boundary — a member watching a group someone else deletes got "Something went wrong!" — so the group and finished-game pages detect the null, say what happened, and navigate away. Only a loader may throw `notFound()`.
- **Notifications are fire and forget.** `buildNotifier` swallows and logs failures so a game never fails because a mail server is down, and the service calls it only after the repository has committed.
- **Motion never hides content.** The reveal animation starts at `opacity: 0.35`, not 0, so a card stays readable if the animation never runs. Same rule for anything added later.
- Migrations are generated (`pnpm db:generate`), never hand-edited once applied. `drizzle/` is copied into `.output/server/drizzle` by the build so the production server can run them.

## Tests

`src/core/game.test.ts` pins the visibility rules — including that someone sitting a game out and a signed-out visitor both see nothing — and `src/server/service.test.ts` drives the whole flow against an in-memory SQLite database, inserting `user` rows directly since accounts are better-auth's to create. It has a suite for the link holder who has not joined; a change to who can see what, or to when a game reveals, belongs in these files first.

Nothing in the suite covers what a browser does with a stream, so anything touching live updates needs driving in two real browser contexts: one page acts, the other must catch up without being touched. That is what proves the stream carries changes and not just that the code compiles. Note that a member's group page holds a request open forever, so it never reaches network idle — a browser script that waits for `networkidle` there will hang until it times out. Wait for an element instead.
